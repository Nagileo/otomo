# Otomo 产品界面与跨端体验重构

> 状态：已实施并完成桌面/移动端、真实账号与生产构建验收
> 目标：把 Otomo 从“带大量调试面板的聊天 Demo”重构为“以任务为中心、可持续使用的 ACGN 工作台”。

## 1. 设计判断

Otomo 的业务能力已经覆盖今日追番、季番导视、个性化推荐、作品档案、收藏分析、订阅与写回。当前主要问题不是缺少工具，而是这些能力只能在聊天中偶然出现，页面结构、回答正文、证据卡片和 Discord 各自表达，导致：

1. 首屏缺少明确任务入口，登录后仍面对空聊天框。
2. 桌面端内容区过窄，固定 Trace 占据空间，移动端信息密度失控。
3. 同一结论由正文与卡片分别生成，可能互相矛盾。
4. 证据、系统状态和用户操作混在一起，普通用户被迫阅读开发信息。
5. 已经成熟的产品工具没有稳定 URL，难以复访、分享和形成使用习惯。

本次重构采用以下原则：

- **任务优先**：固定页面承担高频任务；聊天处理长尾组合需求。
- **单一事实源**：后端工具的结构化结果是正文、面板、分享页和 Discord 的共同数据源。
- **渐进披露**：用户默认看结论、理由和操作；证据详情按需展开；Trace 只在开发模式出现。
- **跨端同能力、不同表达**：网页适合完整工作台；Discord 适合提醒、快速查询、反馈和确认。
- **可恢复状态**：加载、空状态、部分源失败、鉴权过期和写回确认都有明确状态，不用空白页面表达失败。

## 2. 信息架构

### 2.1 主导航

| 路径 | 导航名 | 核心任务 |
|---|---|---|
| `/` | 今日 | 今天更新什么、落后多少、下一步做什么 |
| `/chat` | 对话 | 多跳问答、组合任务、图片/视频输入 |
| `/discover` | 发现 | 季番导视、热播、个性化推荐、媒介切换 |
| `/library` | 收藏 | 收藏统计、口味画像、搁置/抛弃、月报入口 |
| `/subject/[id]` | 作品 | 作品档案、评价、观看入口、系列顺序、音乐和 RSS |
| `/settings/subscriptions` | 订阅 | 提醒规则、渠道、测试推送和发送历史 |

分享页保持公开独立布局，不显示私人导航和开发数据。

### 2.2 App Shell

桌面端：

- 216px 左侧导航：品牌、五个主任务、订阅入口、账号状态。
- 中间内容区：最大 1180px，根据页面使用单列或双列。
- 可选右侧上下文抽屉：证据、执行过程和本轮来源；默认关闭，不永久占位。

移动端：

- 顶部仅保留页面标题、上下文按钮和账号入口。
- 底部固定五项导航：今日、对话、发现、收藏、订阅。
- 所有页面单列；工具操作使用底部动作栏或紧凑按钮组。

## 3. 视觉系统

### 3.1 视觉语义

整体是安静、耐用、偏内容阅读的 ACGN 工具，不做营销首页，也不采用“每块内容都是悬浮卡片”的仪表盘模板。

- 背景：接近墨色的中性黑，不使用蓝灰单色铺满。
- 内容面：深灰黑；边界依靠细线和层级，而不是大面积阴影。
- 主强调色：明亮青绿，表示可执行、已同步和可信。
- 次强调色：暖黄，表示待确认、追番进度和季番热度。
- 风险色：珊瑚红，仅用于错误、剧透和破坏性操作。
- 链接/信息色：清晰蓝色，避免与主操作色混淆。

字号固定为离散 token，不随视口连续缩放。卡片圆角不超过 8px。图标统一使用 Lucide，不使用“图”“新建”这类可由图标表达的方形文字按钮。

### 3.2 设计令牌

- `--bg / --surface / --surface-raised / --line`
- `--text / --muted / --faint`
- `--accent / --accent-strong / --info / --warning / --danger`
- 间距采用 4、8、12、16、24、32、48。
- 固定控制高度 36/40/44px，封面比例统一 2:3。

## 4. 页面设计

### 4.1 今日

首屏不是欢迎语，而是今天真正可执行的队列：

1. 日期、今日更新数量、落后总集数。
2. “今天 / 昨天 / 本周 / 落后 / 隐藏”分段控制。
3. 每个条目显示封面、播出时间、我的进度、已播进度和一个主操作“看完下一集”。
4. 写回必须二次确认；成功后局部刷新。
5. 未登录时显示绑定 Bangumi 的明确入口，同时保留“去发现本季新番”的公开能力，不显示空白。

### 4.2 对话

对话页由三部分组成：会话栏、Answer Document、输入器。

- 历史会话改为可收起列表，不与品牌和账号状态混在一起。
- 回答按事件顺序渲染：解释段落与对应结构化面板相邻。
- 没有显式锚点的面板，在回答末尾按工具执行顺序渲染，不堆到页面底部的第二套“证据区”。
- “依据与来源”只显示关键来源数量和可展开列表。
- Trace、claim 明细、原始 observation 只在开发模式抽屉显示。
- 输入器固定在内容底部，支持图片预览、取消请求和上传状态。

### 4.3 发现

发现页由一个固定筛选条和两个工作区组成：

- 筛选：媒介、场景、题材、冷门/探索模式。
- Anime 季番区：年份、季度、按口味/热度模式；显示每部作品的匹配原因、热度证据、放送时间与命中的导视源。
- 个性化推荐区：五种媒介共享同一推荐卡；支持“更多这种 / 少来这种 / 已看 / 想看 / 换一批”。
- 空结果与冷启动不伪造推荐，直接呈现需要补充的偏好问题。

### 4.4 收藏

收藏页是分析工作台，不是统计卡片墙：

- 顶部媒介切换与总收藏、已评分、平均分。
- 一行分布图：状态分布、评分分布、年代分布。
- 下方按主题分区：高频标签、代表作品、staff/CV/studio、搁置/抛弃、记忆中的好球区与雷区。
- 月报/年报是收藏页的可分享派生视图，不重复拉另一套数据。

### 4.5 作品

作品页由 subject dossier 直接驱动：

- 首屏是封面、标题、元数据、无剧透摘要和主操作。
- 固定页签：概览、口碑、系列、音乐、观看与资源。
- 不认识的通用 section 仍可降级成结构化列表，但不得显示 `[object Object]`。
- 所有外链标明来源和性质；RSS/资源只做导航和订阅，不暗示托管。

## 5. Answer Document 契约

后端结构化 observation 是唯一事实源。前端遵循：

1. `[[panel:tool]]` 与 `[[panel:tool:anchor]]` 决定正文中的明确位置。
2. 已渲染的面板不会在回答底部重复出现。
3. 未锚定面板按首次 observation 顺序追加到正文之后。
4. 面板内部结论只读取 observation；不得再从正文正则推断 OP/ED、集数、评分或观看顺序。
5. 普通模式只展示用户可行动字段；开发模式才展示匹配置信度、冲突原因和原始证据。

## 6. 后端页面 API

固定页面使用显式 API，不暴露任意工具分发：

- `GET /product/season-guide`
- `POST /product/recommendations`
- `GET /product/library`
- `GET /product/monthly-report`
- `GET /product/subjects/{subject_id}`

这些 API 必须：

- 复用现有 Tool，不复制业务算法。
- 从 OAuth session 注入当前 username，不接受客户端冒充私人账号。
- 使用现有限流、tenant scope 与 CSRF 规则。
- 返回标准 `{ok, data, sources}` 或 ToolResult JSON。
- 外部源部分失败时保留可用 section，并在 caveats 中说明。

## 7. Discord 设计

Discord 不复制网页的复杂布局，只承担其擅长的场景：

- `/今日`：今天更新、落后进度、直接“看完下一集”并二次确认。
- `/推荐`：每批最多 5 个条目；按钮支持“更多这种 / 少来这种 / 已看 / 下一批”。
- `/新番`：紧凑导视 embed，保留命中导视 UP 和来源链接。
- 主动推送：每日追番、周报/月报和异动摘要，正文短、链接回网页深页。
- 记忆、剧透和 Bangumi 身份继续按用户隔离；频道上下文只保存短期对话状态。

## 8. 验收标准

1. 1440px 页面不再出现右半屏长期空白；主内容宽度和阅读行长稳定。
2. 390px 页面无横向滚动、无文字溢出，底部导航和输入器不遮挡内容。
3. 普通用户默认看不到 Trace、claim 逐条校验和 observation 原文。
4. 今日、发现、收藏、作品均能不经过聊天直接完成核心任务。
5. 聊天中同一工具面板只出现一次，锚定顺序正确。
6. 页面 API 复用现有工具并通过 OAuth tenant 隔离。
7. Discord 能完成今日查看、推荐反馈、换一批与写回确认。
8. 后端测试、前端 build、Playwright 桌面/移动截图全部通过。
